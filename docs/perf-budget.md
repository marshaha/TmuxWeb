# 性能预算：掉帧算 bug

长历史滚动、多 pane 直播、手机浏览器——这些以前只能靠"感觉卡不卡"。现在有一条可测的线。

## 三个数字

| 指标 | 预算 | 为什么是这个数 |
| --- | --- | --- |
| 帧时间 p95 | ≤ 24ms | 60Hz 下一帧 16.7ms，掉一帧 33ms 已经能看出来；24ms 是"还能忍"的上限 |
| 最长任务 | ≤ 120ms | 再长，点击/输入就明显迟滞 |
| DOM 节点 | ≤ 12000 | 移动端 Safari/Chrome 的布局成本在这里开始非线性 |

## 怎么测

打开 `?perf=1`（或 `localStorage['tmux-perf']='1'`）：左上角一个小方块显示
`fps · p95 · 长任务 · 消息数/节点数`，超预算立刻变红。每 15 秒把一行结果 POST 到
`/api/client-trace`，落在服务日志里：

    render pane=%443 last_id= rendered=500 note=perf fps=58 p95=17.2 task=64 nodes=11840 ok=1

手机上复现卡顿时不用一直盯着屏幕，看一眼日志就有数。

也可以从控制台直接采样：

    await TmuxPerf.sample({ms: 3000})   // 自动滚动 3 秒，返回 {fps, frameP95, longestTask, nodes, verdict}

## 已知的实测数据

* 一条聊天消息 ≈ **24 个 DOM 节点**（300 条 → 7229 节点，含页面框架约 1000 个）。
* 按 12000 节点预算 → 消息上限 **500 条**（`TRANSCRIPT_PAGE_MAX`）。
  原来的 1000 条是 2.4 万节点，实测在本机无 GPU 环境下光"追加 + 布局"就超过 5 秒。
* headless Chrome 里的 fps 数字**不可信**（软件渲染、无合成器）；节点数和长任务是可信的。
  真要判帧率，请在真实 Chrome / 手机上开 `?perf=1` 看。

## 什么时候算 bug

* p95 超过 24ms，或长任务超过 120ms —— 先查是不是又在渲染路径里加了同步重活；
* 节点数超过预算 —— 先看上限/展开逻辑，而不是把虚拟化加回来
  （`content-visibility` 是 #378 崩溃的嫌疑，已经拿掉）。
