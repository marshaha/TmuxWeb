# 等你回答（铃铛）

agent 停下来等人做选择的时候，铃铛亮起来，抽屉里列出"哪个 pane 在等、等的是什么"。

## 亮不亮由三道门共同决定

1. **决定点**：这个 pane 上确实有一个"停下来等你"的动作 ——
   会话文件说它 idle 在等，或宿主机的 agent 上报了 waiting 事件；
2. **屏幕上有菜单**：`agent_prompts.parse_screen` 能认出来（光标列表 / 编号列表 / y-N 确认）；
3. **连续两次扫描稳定**：菜单内容（标题 + 选项 + 光标位置）没变，避免动画/重绘期间抖动。

任何一道不满足都不亮 —— 宁可漏报，不要天天喊狼来了。
hermes 和纯 shell 不在门内（它们的会话文件没有决定信号）。

## 铃铛上的数字是"还开着的"，不是"没点过的"

历史行会一直留着（30 天 / 200 条上限），但它们**不该**继续点亮铃铛。

以前数字取"未读"，于是点过或没点过的旧菜单会永久顶着数字 —— 实测见过
**135 条 open 对 0 个真正在等的 pane**，看起来就是"大量误判"。现在：

* `count` = `resolved_at IS NULL` 的行数（真的还在等）；
* 抽屉默认只列这些；要历史就 `GET /api/needs-you/inbox?history=1`；
* `unread` 仍然单独统计，只用于抽屉里的"未读"样式。

## open 行怎么收敛

| 情形 | 处理 |
| --- | --- |
| 菜单消失 / 换成别的菜单 | 下一次扫描标 `cleared` / `superseded`（内存里记着这次的记录 id） |
| 进程重启 | 启动时把上一进程留下的所有 open 行标 `restarted` —— 没人能再清它们了 |
| 挂了 12 小时还没清 | `prune()` 标 `expired`（菜单大概率早没了，或 pane 已经死了） |

"上一次扫描说它在等"是活着的进程才有的知识，进程一死这份知识就没了；
不归档的话，铃铛会一直指着早已消失的菜单。这一条是本期修的主因。
